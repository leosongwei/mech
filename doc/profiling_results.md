# 对战服务 profiling

服务器是单进程、单线程的 30 Hz 定步长循环（`backend/server/main.py::game_loop`）：
`world.update(dt)` 跑完整条系统管线，然后 `broadcast` 打包快照。线上它靠 `asyncio.sleep`
压在 30 Hz，所以"一个 tick 到底花多少 CPU"平时是看不见的。这份报告把 sleep 拿掉，
**能跑多快跑多快**，测的是同一个 tick 的计算开销。

## 方法

工具：`tools/profile_battle.py`（本次新增，见 AGENTS.md）。

* 一把 `World(seed=11, mode="battle")`、两个脚本化飞行员（红蓝各一，输入是 tick 的
  纯函数，所以每个时长跑的都是同一场仗的不同长度）。
* **不留余量地连跑**：`for tick in range(ticks): world.update(1/30)`，不看墙上时间。
* 三路测量：
  1. **逐系统**：把 `world.systems` 每个条目包一层 `perf_counter_ns`，另外单独计
     `grid.build` 和 `World.update` 剩下的部分（合计 ~2 µs/tick，可忽略）；
  2. **netcode**：每 2 tick 一次 `snapshot_bytes`、每 3 tick 每个飞行员一次
     `meta_payload`，按 tick 摊平（这是 `broadcast` 在同一个进程里真花的钱）；
  3. **cProfile**：同一场仗再跑一遍，拿函数级的 tottime / cumtime 排名。
     cProfile 会把每次 Python 调用都记一笔，本身放大约 1.7 倍（5 分钟档：6.7 →
     11.6 ms/tick），且偏袒"调用密集"的代码，所以**只用它排名，不用它报绝对时间**：
     绝对时间以第 1 路的数字为准。
* 机器：AMD Ryzen 7 5800X3D，Python 3.12（`.venv`），numpy 2.5，单线程单进程。

时限：5 / 10 / 20 / 30 分钟**游戏时间**（9000 / 18000 / 36000 / 54000 tick）。

## 一个前提：实体数在涨

`modes/battle/waves.py` 的增援波没有上限，双方每波都补人，所以**这四档测的不只是
"跑多久"，而是"战场上有多少单位"**。第 1 分钟 64 个实体、第 5 分钟 244 个，其中
`combat` 从 14 涨到 192。所有系统都是"每单位一个 Python 循环"，所以成本基本正比于
单位数——这一条比任何单点优化都重要，后面每一档都会看到它。

| `netcode.snapshot_bytes` | 8.1 % | 每 2 tick 一次，随实体数线性 |
| `waves.run` | 3.6 % | `_capture` 每 tick 重算城镇争夺 |

### 结论（5 分钟）

1. **最大的单一是"Python 里的地形采样"**。`terrain._march`（5.7 s 自身）驱动
   `height_at`（**350 万次**）、`tile_type`（**870 万次**）、`blocked`（870 万次）、
   `trunk_blocked`/`trunk_hit`，这些纯 Python 标量函数加起来约占 update 的 1/3。
   它的三个入口都很"值钱"：AI 的视线检查（`ai._sees`，10.9 s）、每发子弹的弹道解
   （`weapons.fire → sight_point`，7.3 s）、每个车体的碰撞（`movement._blocked`，9.1 s），
   再加上弹丸落地（`projectiles.ground_hit`，4.0 s）。同一条射线沿 8 m 一步在 Python
   里走，是这套代码最贵的原语。
2. **AI 的第二块是选目标**：`_acquire` 每次都 `grid.box` + `_unique` + 距离排序
   （9.9 s），而它的候选集随单位数增长——这也是 `ai.run` 占比从 2 分钟时的 13 % 涨到
   33 % 的主要原因。
3. **ECS 视图开销是普税**：`ecs._gather` 15.5 s、`__getitem__` 21.4 s（累计）铺在所有
   系统里，`np.ndarray.item()` 被调用 **2888 万次**（3.2 s）——把 numpy 标量一个个转成
   Python 数的那一层，本身已经是可以看见的成本。
4. **netcode 不是零**：快照 + meta 摊到每个 tick 是 0.80 ms，占 tick 总开销的 12 %，
   且随实体数线性（每 2 tick 打包一次 ~1.6 ms）。

### 结论（10 分钟）

1. **`terrain._march` 是全局的底座**：它不在任何一家系统里，却被四家同时用（AI 视线、
   弹道归零、车体碰撞、弹丸落地）。10 分钟窗口里它被调用 52.7 万次，每次都在 8 m
   步长上 `height_at` / `tile_type` / `blocked`。**优化它一次，四家同时受益**，
   而且它是最容易向量化/缓存的一块（高度场与墙高本来就是 numpy 数组）。
2. **`weapons.fire → zero_pitch → sight_point` 从 11 % 涨到 23 %**：每发弹丸发射前都要
   先找"十字线指着什么"（`sight_point`），再解发射仰角。10 分钟窗口里 12058 发 =
   每秒 100 发**。注意贵的是前半截，不是"解"**：`zero_pitch` 29.7 s 里
   `sight_point` 占 29.5 s，其中 `_unit_hit`（对所有单位、每个命中球做射线-球求交，
   纯 Python 双层循环）16.4 s、地形走查约 11 s；真正的高阶解 `solve_elevation`
   只有 **0.14 s**（子弹是闭式解，火箭的割线法很少走）。所以这一行要按"向量化求交"
   来改，而不是缓存"归零解"。
3. **`ai._sees` 占了 AI 的 50 %**：每次选目标都要对每个候选做一次视线检查，而每个
   候选的打点是一条 `_march`。选目标的候选集随单位数涨（`_acquire` 15.9 s），于是
   AI 成本是"单位数² × 射线长度"。
4. **`projectiles.run` 变成第一**：它自己的主循环是纯 Python 的逐发弹丸（每发一次
   `sphere_table` 查询 + 一次 numpy 小数组运算），配合 `linalg.norm`（4.4 s）这种
   "对小数组调 numpy"的写法，开销比数学本身大得多。
5. ECS 视图税从 5 分钟的 ~35 s/9000 tick 涨到 22.3+11.4 s/3600 tick——**每单位每 tick
   的视图取用次数没有变，但单位多了 30 %、系统次数没变，所以它跟着线性涨**。

### 结论（20 分钟）

1. **成本已经"平台化"**：19 ms/tick，且形状与 10 分钟一致（四家 91 %）。也就是说，
   后面再跑多久，只要场上单位数与火力密度相当，就是这条曲线；**30 分钟的看点是有没有
   新的量变**（单位数继续涨 / 弹丸更多 / 一场攻城战把所有 raider 挤在一起）。
2. **`terrain._march` 的账单不再隐藏在某个系统里**：10 分钟窗口它是 33 s/3600 tick，
   20 分钟是 23 s/3600 tick（因为武器开火少了、`sight_point` 从 12k 降到 6.8k 发），
   但它始终是四家共同的底座——`height_at`、`tile_type`、`blocked` 三个纯 Python 标量
   函数每个窗口被调用 **500–1000 万次**。
3. **`weapons.fire` 的钱花在"找瞄准点"，不在"解仰角"**：6779 发弹丸共 19.6 s，
   其中 `sight_point` 19.6 s（`_unit_hit` 13.1 s + 地形走查 ~5.4 s），而
   `solve_elevation` 只有 **0.15 s**（子弹闭式、火箭割线）。所以：① `_unit_hit` 要
   跟弹丸的扫掠一样**向量化**（一次 numpy 解所有候选单位的所有球），② 更省事的做法是
   **复用本 tick 已经建好的命中球表**（`world.sphere_table`，弹丸系统每 tick 都要建），
   别再用 `mu.unit_spheres` 逐炮塔重建一遍；③ 只有"给定 (wid, d, h) 的仰角解"这一层
   是纯函数、可以缓存，但它本来就不贵。
4. **`ai._acquire` 与 `_sees` 是"单位数 × 候选数"**：16.6 s + 22.3 s（折算各自约
   1.9 / 2.5 ms/tick）。注意**选目标本来就是 0.45 s 一次的节流查询**（`ai_timer`），
   每 tick 花掉的是"我已经锁定的那个目标现在还看得见吗"——每 tick 约 25 次射线、每次
   ~100 µs，是打/停火的那一拍。可行的减法不是"按格子缓存 1 s"（山脊线上 1 s 足够让
   答案翻面），而是脏检查：眼或目标位移 > 5 m 才重算，或每 4 tick 一次、各车错开相位。
5. **netcode 不是瓶颈**（5.1 %，978 µs/tick），但它随实体数线性；每 2 tick 打包
   ~2 ms，其中 `_gather`/`item()` 占大头——快照是 numpy 取列 + `.item()` 拼字节的活。

### 结论（30 分钟）

1. **成本结构在 5 分钟就定型了**：`projectiles` + `ai` + `weapons` + `movement` 在
   5 / 10 / 20 / 30 分钟分别是 84.9 % / 91.5 % / 91.9 % / 91.7 %；单 tick 均值
   6.7 → 13.5 → 19.0 → 17.2 ms（第 4 档更低是因为中途重开了一局，样本被"干净战场"
   稀释）。**要提速，只需要动这四家，其余十四家加起来 < 9 %。**
2. **30 Hz 的预算在这个规模下已经越线**：预算是 33.3 ms/tick，而满编对局的中后段
   （350–460 个实体、100 发左右在飞的弹丸）**分钟均值就到了 20–46 ms**，其中第 29、
   30 分钟（46.2 / 39.4 ms）明确超过预算——那几段 `game_loop` 会走 `delay < 0` 的
   补跑分支（`next_t` 被重置），玩家感知是"卡一下"而不是平滑降速。分钟均值只是下界
   性质的证据；**逐 tick 分位数这次没有采**（harness 现在已经会记 p50/p90/p99 与
   超预算 tick 占比，下次跑就有）。
3. `raids.run` 平均只占 1.7 %，但**单 tick 最坏 46.9 ms**：A* + 两级寻路的规划一 tick
   做完，一次派兵就能让那个 tick 越过预算。它是"偶发尖峰"型，不值得优化均值，
   但值得分摊（每 tick 只推进一个 raider 的规划）。
4. 与 20 分钟相比没有新的量变：没有新的系统变成热点，没有缓存爆掉，`smoke`/`debris`/
   `locking` 依然是 0。**唯一的新事件是整局重置**（一 tick 的重建成本 + 之后几分钟的
   "干净战场"便宜期）。

还没到那份上。**收益全在成熟对局**——这正是本节存在的理由。

### 1. `terrain._march`：不向量化，只做标量内联

⚠ 处方里写的"按 tile 用向量化采样"是**错的**，实测做出来更慢：一条 36 m 的射线
只有 ~5 个采样点，走 numpy 就变成十几次小数组调用（`np.fmin`、`argmax`、fancy
index），5 分钟档累计 12.7 万次小调用，**36 m 射线从 13.5 µs 涨到 135 µs**。当场
回滚。

真正有效的是把标量路径上的常数开销拿掉，结果是**位级一致**的：

* `_spans` 生成器内联成 `while` 循环（原来每步一次 `yield` + 一次 `next`）；
* 一个闭包 `sample(x, z)` 替掉 `obstacle_at` / `sight_at` 的"地面 + 墙"两次调用，
  并缓存上一个 tile 的四个角点高度（8 m 步长下约一半采样直接命中缓存）；
* 树先查一次 `t_item(j, i) in (TILE_TREE, TILE_FOREST)`，再进 `_trunk_hit` /
  `_canopy_hit`，`trunk_of` / `canopy_of` 提到循环外当局部变量。

实测：36 m 13.1 → 8.2 µs，400 m 68 → 34.5 µs，1.5 km 154 → 75 µs（1.5–2×）。
累到系统上就是 `ai.run` −29 %（视线）、`weapons.run` 的一部分（弹道归零）、
`movement.run` −6 %（车体碰撞）、`projectiles.run` 的一部分（弹丸落地）。

顺带一个**可用来说明"该优化谁"的数**：`_march` 的调用里 **87.6 % 是 ≤ 50 m 的
`ground_hit`（一条弹丸腿）**，只有 12.4 % 是 `los`（300–5000 m）。所以快的是
"短射线的那几个采样点"，不是"远处的长射线"。

### 2. `ballistics.sight_point`：复用一张表，且知道它是什么时候的

`world.aim_spheres()` 返回 `(sph, row_ok)`：本 tick 的表如果还没建（`_sph` 空或
是上一 tick 的），就**自己建一张并打上 `_sph_premove`**；`row_ok` 每 tick 校验一次
"这些 id 还是不是活着的、拥有命中球的单位，且表里的球心和我现在的 `pos` 差 < 10 m"，
不成立就返回 `None`，调用方回退到逐台建球。`sphere_table()` 看到 `_sph_premove` 会
重建一张"移动后"的表，扫掠因此拿不到瞄准时（移动前）的那张。
`ballistics._unit_hit` 也从"逐台 `mu.unit_spheres`"改成对整张表一次向量化射线-球。

`weapons.run`：20 分钟档 3135 → 1662 µs/tick（−47 %），5 分钟档 668 → 527。
精度：1029 次随机瞄准与"逐台建球"的旧解对比，**0 处不一致，最差点差 0.00 mm**。

### 3. `projectiles.run`：批量的是地形碰撞，不是积分

⚠ "按 wid 分组把 98 % 的弹丸整批积分"也是错的，试过、**没有收益甚至更慢**：逐组
numpy 调用的开销大于省下来的标量运算（每类弹丸每 tick 一次 `np.linalg.norm` +
`minimum` 对 1–5 行，纯亏），已回滚。

有效的是把**地形碰撞**批起来。`terrain.ground_hits_many(p0, p1, step=9.0)` 对一批
腿一次算完 `obstacle_at`（地面 + 墙），返回 `(hit, t_hit, walk)`；`walk` 标记"这条腿
穿过了树格"，交给标量 `ground_hit` 去做（树干是解析求解的圆柱，不能采样）。
`projectiles.run` 因此拆成两趟：pass 1 飞每一发、把 `p0/p1` 记进 `legs0/legs1`；
一次 `ground_hits_many`；pass 2 按**升序 pid** 做碰撞和爆炸副作用（实体创建顺序不变）。

批量 **0.8 µs/腿 vs 标量 8.2 µs**；`projectiles.run` 20 分钟档 5885 → 4303 µs/tick
（−27 %）。

**精度**：4000 条随机腿（同样的 9 m 步长）与 `ground_hit` 对拍，**0 处"命中 / 不命中"
分歧，爆点位置最差差 0.0077 条腿 ≈ 0.2 m**（就是 9 m 采样上二分 6 次的分辨率）。314 条
腿被交给标量走查：采样点落在树格里的，以及起点就在树格里的。后者是这一版才修掉的
——采样原先从 `f = 1/n` 开始，腿的**起点那一格压根没被采样**，于是一条起点在树里的腿
会从树干边上溜过去（树格只查 tile，树干是解析求解的圆柱）。现在两端都采，`n + 1` 个点。

**剩下的松处**：一条只在两个采样点之间擦过树格一角的腿，不会被判给标量走查（16 m 的
格子对 9 m 的步长，只有角落才可能，4000 条腿里没有出现）；以及爆点有 0.2 m 的分辨率。
两者都写在 `ground_hits_many` 的 docstring 里。

0.2 m 的爆点偏移足以让 1 分钟的脚本化对战分叉：`tools/replay.py` 从第 ~110 tick 起
`n_all` 差一个、`hp_total` 差 0.02 %，整场于是走了另一条路（`--save` 重基线）。
为了确认**分歧只来自这里**，把 `ground_hits_many` 强行改成"每一腿都交给标量走查"再跑
一遍：900 tick 与**重基线之前**的旧 fixture 逐项相同，0 处不同。也就是说地形走查
（第 1 项）、瞄准（第 2 项）和快照（第 4 项）**一个数都没动**，动的只有弹着点的最后
0.2 m。

### 4. ECS 视图税：一次解析，多列一起取

⚠ 报告把这一项归给 `ndarray.item()`（4200–5300 万次）。查下来 `.item()` 的绝大部分
来自旧 `_march` 里的 `height_at`（**每次采样 4 次**），第 1 项做完它就没了。剩下的是
`_gather` 本身。

试过一条"单 archetype 快路径"（`where` 全等于同一个 archetype 就跳过多重掩码），
**真实对局里 12927 次多 id 读取中命中 0 次**——`all_units()` 永远是 2–3 个 archetype
（有手的机甲 / 无手的车 / 步兵）的混合，所以撤掉了。

真正有效的是 `ECS.columns(ids, names)`：**archetype 划分只解析一次**，之后每一列
只是一次 gather + 一次赋值。`netcode.snapshot_bytes` / `hp_columns` 改用它（单位块 20
列、弹丸块 5 列、烟幕块 3 列）。实测 65 个 id × 20 列：逐列走 `View` 654 µs，
`columns` 126 µs（**5.2×**）。netcode 摊到每 tick 1019 → 351 µs（**−66 %**）。

正确性：同一个 seed 跑 3000 tick，每 10 tick 一张快照，新旧 `snapshot_bytes` 的输出
**逐字节相同**（sha256 `684637ab…`，1903272 B）。

## 总结：钱都花在哪

四档合起来只有一句话：**这套模拟的瓶颈不是 numpy 算得慢，而是每 tick 有 7–8 万次
Python 函数调用，每一次都在做"标量级"的活**（沿射线取一格地形高度、算一个球的位移、
把一个 numpy 标量转成 Python float）。所有热点都是这条的变体。

按"占比 × 是否好改"排出的清单（这是**优化前**的处方：`#1`、`#2`、`#5`、`#6` 已在
上一节落地；其中 `#1`、`#5`、`#6` 三条的具体做法被实测否掉了，以那一节为准）：

| # | 位置 | 占比（30 分钟窗口） | 为什么贵 | 怎么改 |
| --- | --- | ---: | --- | --- |
| 1 | `terrain._march`（`height_at` / `tile_type` / `blocked` / `trunk_*`） | 22 %，被四家共用 | 每 tick 159 次射线走查，8 m 一步，每步几个纯 Python 标量函数；单次 62 µs | 高度场与墙高**本来就是 numpy 数组**：把一段射线按 tile 用向量化采样（`_spans` 已经算出格子序列，直接 fancy-index 取 `heights[z, x]` 并 `argmax` 找第一个挡住的格），把 8 m 采样与二分留在 numpy 里。这一处会让 ai / weapons / movement / projectiles **同时**变快 |
| 2 | `ballistics.sight_point`（从 `weapons.fire → zero_pitch` 进） | 19 %（30.4 s；`solve_elevation` 只有 0.2 s） | 每发弹丸发射前都要对**射程内每台车体的每个命中球**做射线-球求交。10 分钟窗口拆开：`_unit_hit` 16.4 s，其中**逐台重建球 9.2 s**（`unit_spheres` → `sphere_world` 每次只算 1 行 + 造 Python tuple，`unit_spheres` 全库只有这一个调用点）、求交数学 5.7 s；`sight_point` 另外约 11 s 是地形走查 | ① 只读复用**上一 tick 建好的** `sphere_table`（正是 tick 开始时的位置，见下注），零额外建表成本；② 射线-球求交向量化（一次 numpy 解全部候选球）；③ 剩下 11 s 是地形走查，同第 1 条；④ 仰角解 `(wid, d, h)` 可缓存，但它只占 0.7 %，先别管 |
| 3 | `ai._sees → sight.clear → terrain.los` | 14 %（22 s；折算约 **2.5 ms/tick，每 tick 25 次、每次 ~100 µs**） | **选目标已经节流**（`ai_timer` 0.45 s × 抖动），每 tick 这次是"我现在还看得见他吗"——打/停火那一拍；每条都是完整 `_march` | 脏检查节流：眼或目标位移超过 ~5 m 才重算，或每 4 tick（0.13 s）重算一次、各车错开相位。不要用 `(观察者格, 目标格)` 缓存 0.5–1 s——答案会在山脊线上翻面，1 s 太久。更根本的是把 `_march` 本身做快（第 1 条），那样这 2.5 ms 直接变几百 µs 且没有滞后 |
| 4 | `ai._acquire`（`grid.box` + `_unique` + 距离排序） | 10 %（16.6 s） | 每 tick 每个 AI 单位筛一遍 1.5 km 内的所有目标，候选集随单位数涨 | 只对"换了格子/换了目标集"的单位重算；`grid.box` 的结果按 (格子, 半径) 缓存一 tick |
| 5 | `projectiles.run` 主循环 + `sphere_table` | 35 %（54.7 s，其中自身 13 s） | 逐发弹丸一个 Python 循环：制导、地形碰撞、命中解算、写回 ECS；每 tick 还重建整张球表（`sphere_world` 5.5 s） | **整批向量化真正需要的是"每发的更新是同一条逐行公式"，不是"轨迹是直线"**：在飞的弹丸里 **50.6 % 是子弹、48.6 % 是 S-8 火箭**（实测 4 分钟、峰值 110 发），这两类都是同一条公式逐行作用（子弹 `v.y -= g dt`；火箭"归一化→加速→再加重力"，全是 `v/|v|`、`min`、加法），**按 wid 分组各一遍 numpy 就能算完 98 % 的弹丸**；只有 SACLOS（0.8 %）和攻顶要逐发分支（看射手的视线 / 寻的 + `sight.why`）。同 tick 内每发走的仍是一条**直线腿**（半隐式欧拉每步就是直线，抛物线是逐步的包络），所以扫掠与地形碰撞仍旧是"线段对球 / 线段对地形"，只是候选集可以批量取、批量解，最后用 `minimum.reduceat` 按弹丸取最早命中；命中后的副作用（`blasts.spawn`/`combat.hit`/销毁）按弹丸 id 升序逐发做，保持和现在一样的实体创建顺序 |
| 6 | ECS 视图税（`__getitem__` / `_gather` / `item()`） | 21 % | 每 tick 1113 万次视图取用、5317 万次 `ndarray.item()` | 系统内用 `groups()` 把 buffer 一次取出（已有范式）；`float(row[0])` 改成取 numpy 标量或用 `.tolist()`；`min/max` 内置调用（2600 万次）换成 `np.clip`/比较 |
| 7 | `raids.run` 规划 | 1.7 % 均值，**单 tick 47 ms** | A* + 两级寻路一次做完 | 每 tick 推进一个 raider 的规划（限制每 tick 的规划预算） |
| 8 | `netcode.snapshot_bytes` | 5.5 %（936 µs/tick） | 每 2 tick 打包 400+ 实体 × 72 B，靠 `.item()` 拼字节 | 不是瓶颈；要削可以整列 `tobytes()` 拼 |

> **注：瞄准射线本来就可以用那张表——用"上一 tick 建好的那张"。**
> 一张 `sphere_table` 约 **1.3 ms**（30 分钟窗口 3600 次建表 4.66 s = 1.00 次/tick）。
> 时序是这样的：`weapons.run` 在 `movement.run` **之前**，此时单位的 `pos` 就是本 tick
> 开始时的位置（上一 tick movement 的结果）；而 `sphere_table` 在 `projectiles.run` 里
> 建，单位是"本 tick 结束时的位置"、`prev = pos - vel*dt`，这是扫掠解算要的那一份。
> 所以：
> * **瞄准/锁定的射线要的是 tick 开始时的位置**，而它恰好等于**上一 tick 建好的那张表**
>   （`world.update` 开头把 `_sph` 清掉了，这纯属白扔）。让 `weapons`/`ai` 只读地用上一
>   tick 的表，**零额外建表成本**，一次性拿到 `unit_spheres` 那 9.2 s / 窗口；
> * 想在 `weapons` 时**新建**一张也行，那就必须在 `movement` 之后显式作废、让弹丸重建
>   一次（1 → 2 次/tick，+1.3 ms/tick），换 2.5 ms/tick 的射线建球——仍然划算，但不如
>   上面那一条干净；
> * 无论哪种，求交数学（5.7 s）都要向量化，球表只解决"球在哪"。
>
> 唯一的约束是帧号：`reset_match` 会把实体全销毁、id 全变，那张表要跟着作废（顺带
> `world._sph_tick` 也得跟着走），不能跨局复用。
>
> （**已按第三条落地**：`world.aim_spheres()` 在 `weapons` 时若手上没有本 tick 的表就
> 自己建一张、并标记 `_sph_premove`，弹丸那边的 `sphere_table` 看到标记会重建，所以
> 扫掠永远拿不到"移动前"的表。实测 `weapons.run` −47 %，见上一节。）

**不建议动的**：`smoke` / `locking` / `blasts` / `debris` / `economy` / `rearm` /
`gunnery` / `mortality` 全部 < 1 %，加起来不到 3 %；`grid.build` 0.5 %。盯着它们优化
是白费力气。

**一句话版本**：这套模拟的贵，三个字——**小调用**。凡是"每 tick 上万次、每次只有几个
元素的 numpy 调用"的地方（沿射线取一格高度、逐台建一个命中球、逐列走一次 archetype
划分），把它搬到**更大的批次**上（一条腿的整段采样、一张表的一次求交、一次解析多列）
就是收益；反过来把**已经在标量路径上**的循环改写成小数组调用，是纯亏——两种都试过，
前者 20 分钟档拿掉 30 % 的 tick 时间（18.98 → 13.28 ms/tick），后者每处都更慢。
`tools/replay.py` 会当场告诉你有没有改变模拟（它对比的就是数值总和）。
