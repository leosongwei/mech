# 对战服务 profiling

服务器是单进程、单线程的 30 Hz 定步长循环（`backend/server/main.py::game_loop`）：
`world.update(dt)` 跑完整条系统管线，然后 `broadcast` 打包快照。线上它靠 `asyncio.sleep`
压在 30 Hz，所以"一个 tick 到底花多少 CPU"平时是看不见的。这份报告把 sleep 拿掉，
**能跑多快跑多快**，测的是同一个 tick 的计算开销。

## 方法

工具：`tools/profile_battle.py`（本次新增，见 AGENTS.md）。

* 一把 `World(seed=11, mode="battle")`、两个脚本化飞行员（红蓝各一，输入是 tick 的
  纯函数，所以每个时长跑的都是同一场仗的不同长度）。
* **不留余量地连跑**：`for tick in range(ticks): world.update(1/30)`，不看墙上时间。
* 三路测量：
  1. **逐系统**：把 `world.systems` 每个条目包一层 `perf_counter_ns`，另外单独计
     `grid.build` 和 `World.update` 剩下的部分（合计 ~2 µs/tick，可忽略）；
  2. **netcode**：每 2 tick 一次 `snapshot_bytes`、每 3 tick 每个飞行员一次
     `meta_payload`，按 tick 摊平（这是 `broadcast` 在同一个进程里真花的钱）；
  3. **cProfile**：同一场仗再跑一遍，拿函数级的 tottime / cumtime 排名。
     cProfile 会把每次 Python 调用都记一笔，本身放大约 1.7 倍（5 分钟档：6.7 →
     11.6 ms/tick），且偏袒"调用密集"的代码，所以**只用它排名，不用它报绝对时间**：
     绝对时间以第 1 路的数字为准。
* 机器：AMD Ryzen 7 5800X3D，Python 3.12（`.venv`），numpy 2.5，单线程单进程。

时限：5 / 10 / 20 / 30 分钟**游戏时间**（9000 / 18000 / 36000 / 54000 tick）。

## 一个前提：实体数在涨

`modes/battle/waves.py` 的增援波没有上限，双方每波都补人，所以**这四档测的不只是
"跑多久"，而是"战场上有多少单位"**。第 1 分钟 64 个实体、第 5 分钟 244 个，其中
`combat` 从 14 涨到 192。所有系统都是"每单位一个 Python 循环"，所以成本基本正比于
单位数——这一条比任何单点优化都重要，后面每一档都会看到它。

| `netcode.snapshot_bytes` | 8.1 % | 每 2 tick 一次，随实体数线性 |
| `waves.run` | 3.6 % | `_capture` 每 tick 重算城镇争夺 |

### 结论（5 分钟）

1. **最大的单一是"Python 里的地形采样"**。`terrain._march`（5.7 s 自身）驱动
   `height_at`（**350 万次**）、`tile_type`（**870 万次**）、`blocked`（870 万次）、
   `trunk_blocked`/`trunk_hit`，这些纯 Python 标量函数加起来约占 update 的 1/3。
   它的三个入口都很"值钱"：AI 的视线检查（`ai._sees`，10.9 s）、每发子弹的弹道解
   （`weapons.fire → sight_point`，7.3 s）、每个车体的碰撞（`movement._blocked`，9.1 s），
   再加上弹丸落地（`projectiles.ground_hit`，4.0 s）。同一条射线沿 8 m 一步在 Python
   里走，是这套代码最贵的原语。
2. **AI 的第二块是选目标**：`_acquire` 每次都 `grid.box` + `_unique` + 距离排序
   （9.9 s），而它的候选集随单位数增长——这也是 `ai.run` 占比从 2 分钟时的 13 % 涨到
   33 % 的主要原因。
3. **ECS 视图开销是普税**：`ecs._gather` 15.5 s、`__getitem__` 21.4 s（累计）铺在所有
   系统里，`np.ndarray.item()` 被调用 **2888 万次**（3.2 s）——把 numpy 标量一个个转成
   Python 数的那一层，本身已经是可以看见的成本。
4. **netcode 不是零**：快照 + meta 摊到每个 tick 是 0.80 ms，占 tick 总开销的 12 %，
   且随实体数线性（每 2 tick 打包一次 ~1.6 ms）。

数。

### 结论（10 分钟）

1. **`terrain._march` 是全局的底座**：它不在任何一家系统里，却被四家同时用（AI 视线、
   弹道归零、车体碰撞、弹丸落地）。10 分钟窗口里它被调用 52.7 万次，每次都在 8 m
   步长上 `height_at` / `tile_type` / `blocked`。**优化它一次，四家同时受益**，
   而且它是最容易向量化/缓存的一块（高度场与墙高本来就是 numpy 数组）。
2. **`weapons.fire → zero_pitch → sight_point` 从 11 % 涨到 23 %**：每发弹丸发射前都要
   先找"十字线指着什么"（`sight_point`），再解发射仰角。10 分钟窗口里 12058 发 =
   每秒 100 发**。注意贵的是前半截，不是"解"**：`zero_pitch` 29.7 s 里
   `sight_point` 占 29.5 s，其中 `_unit_hit`（对所有单位、每个命中球做射线-球求交，
   纯 Python 双层循环）16.4 s、地形走查约 11 s；真正的高阶解 `solve_elevation`
   只有 **0.14 s**（子弹是闭式解，火箭的割线法很少走）。所以这一行要按"向量化求交"
   来改，而不是缓存"归零解"。
3. **`ai._sees` 占了 AI 的 50 %**：每次选目标都要对每个候选做一次视线检查，而每个
   候选的打点是一条 `_march`。选目标的候选集随单位数涨（`_acquire` 15.9 s），于是
   AI 成本是"单位数² × 射线长度"。
4. **`projectiles.run` 变成第一**：它自己的主循环是纯 Python 的逐发弹丸（每发一次
   `sphere_table` 查询 + 一次 numpy 小数组运算），配合 `linalg.norm`（4.4 s）这种
   "对小数组调 numpy"的写法，开销比数学本身大得多。
5. ECS 视图税从 5 分钟的 ~35 s/9000 tick 涨到 22.3+11.4 s/3600 tick——**每单位每 tick
   的视图取用次数没有变，但单位多了 30 %、系统次数没变，所以它跟着线性涨**。

### 结论（20 分钟）

1. **成本已经"平台化"**：19 ms/tick，且形状与 10 分钟一致（四家 91 %）。也就是说，
   后面再跑多久，只要场上单位数与火力密度相当，就是这条曲线；**30 分钟的看点是有没有
   新的量变**（单位数继续涨 / 弹丸更多 / 一场攻城战把所有 raider 挤在一起）。
2. **`terrain._march` 的账单不再隐藏在某个系统里**：10 分钟窗口它是 33 s/3600 tick，
   20 分钟是 23 s/3600 tick（因为武器开火少了、`sight_point` 从 12k 降到 6.8k 发），
   但它始终是四家共同的底座——`height_at`、`tile_type`、`blocked` 三个纯 Python 标量
   函数每个窗口被调用 **500–1000 万次**。
3. **`weapons.fire` 的钱花在"找瞄准点"，不在"解仰角"**：6779 发弹丸共 19.6 s，
   其中 `sight_point` 19.6 s（`_unit_hit` 13.1 s + 地形走查 ~5.4 s），而
   `solve_elevation` 只有 **0.15 s**（子弹闭式、火箭割线）。所以：① `_unit_hit` 要
   跟弹丸的扫掠一样**向量化**（一次 numpy 解所有候选单位的所有球），② 更省事的做法是
   **复用本 tick 已经建好的命中球表**（`world.sphere_table`，弹丸系统每 tick 都要建），
   别再用 `mu.unit_spheres` 逐炮塔重建一遍；③ 只有"给定 (wid, d, h) 的仰角解"这一层
   是纯函数、可以缓存，但它本来就不贵。
4. **`ai._acquire` 与 `_sees` 是"单位数 × 候选数"**：16 s + 16 s，两个都是随部队规模
   平方增长的结构。1.5 km 内 400 个目标时，每 tick 每个 AI 单位都要筛一遍候选并逐个
   做视线检查（每次一条 `_march`）。视线结果按 (观察者格, 目标格) 缓存一秒，或者把
   "谁看得见谁"整体降到每单位每 2–3 tick 算一次，就能砍掉一半以上。
5. **netcode 不是瓶颈**（5.1 %，978 µs/tick），但它随实体数线性；每 2 tick 打包
   ~2 ms，其中 `_gather`/`item()` 占大头——快照是 numpy 取列 + `.item()` 拼字节的活。

两条要点：

1. **第 21 分钟是整局重置**（`wave` 回到 1、实体从 452 掉到 62）：30 分钟的游戏时间里
   打了 **1.4 局**，指挥部被端掉后 `reset_match` 重开。重置那一 tick 自己要 12.96 ms
   的分钟均值，因为那一下要销毁 450 个实体再重建基地与平民。
2. **单位数是波动的、不是单调的**：两侧的 raider 会互抄后路、部队在交战中损失，所以
   400–530 的实体数会在十几分钟内来回摆动（20 分钟 452 → 25 分钟 249）。真正和成本
   强相关的是**当下这个 tick 的火力密度**：第 29 分钟只有 430 个实体、89 发在飞的弹丸，
   却是 46 ms/tick（弹丸数在一分钟内峰值到 125）。

### 结论（30 分钟）

1. **成本结构在 5 分钟就定型了**：`projectiles` + `ai` + `weapons` + `movement` 在
   5 / 10 / 20 / 30 分钟分别是 84.9 % / 91.5 % / 91.9 % / 91.7 %；单 tick 均值
   6.7 → 13.5 → 19.0 → 17.2 ms（第 4 档更低是因为中途重开了一局，样本被"干净战场"
   稀释）。**要提速，只需要动这四家，其余十四家加起来 < 9 %。**
2. **30 Hz 的预算在这个规模下已经越线**：预算是 33.3 ms/tick，而满编对局的中后段
   （350–460 个实体、100 发左右在飞的弹丸）**分钟均值就到了 20–46 ms**，其中第 29、
   30 分钟（46.2 / 39.4 ms）明确超过预算——那几段 `game_loop` 会走 `delay < 0` 的
   补跑分支（`next_t` 被重置），玩家感知是"卡一下"而不是平滑降速。分钟均值只是下界
   性质的证据；**逐 tick 分位数这次没有采**（harness 现在已经会记 p50/p90/p99 与
   超预算 tick 占比，下次跑就有）。
3. `raids.run` 平均只占 1.7 %，但**单 tick 最坏 46.9 ms**：A* + 两级寻路的规划一 tick
   做完，一次派兵就能让那个 tick 越过预算。它是"偶发尖峰"型，不值得优化均值，
   但值得分摊（每 tick 只推进一个 raider 的规划）。
4. 与 20 分钟相比没有新的量变：没有新的系统变成热点，没有缓存爆掉，`smoke`/`debris`/
   `locking` 依然是 0。**唯一的新事件是整局重置**（一 tick 的重建成本 + 之后几分钟的
   "干净战场"便宜期）。

## 总结：钱都花在哪

四档合起来只有一句话：**这套模拟的瓶颈不是 numpy 算得慢，而是每 tick 有 7–8 万次
Python 函数调用，每一次都在做"标量级"的活**（沿射线取一格地形高度、算一个球的位移、
把一个 numpy 标量转成 Python float）。所有热点都是这条的变体。

按"占比 × 是否好改"排出的清单：

| # | 位置 | 占比（30 分钟窗口） | 为什么贵 | 怎么改 |
| --- | --- | ---: | --- | --- |
| 1 | `terrain._march`（`height_at` / `tile_type` / `blocked` / `trunk_*`） | 22 %，被四家共用 | 每 tick 159 次射线走查，8 m 一步，每步几个纯 Python 标量函数；单次 62 µs | 高度场与墙高**本来就是 numpy 数组**：把一段射线按 tile 用向量化采样（`_spans` 已经算出格子序列，直接 fancy-index 取 `heights[z, x]` 并 `argmax` 找第一个挡住的格），把 8 m 采样与二分留在 numpy 里。这一处会让 ai / weapons / movement / projectiles **同时**变快 |
| 2 | `ballistics.sight_point`（从 `weapons.fire → zero_pitch` 进） | 19 %（30.4 s；`solve_elevation` 只有 0.2 s） | 每发弹丸发射前都要对**所有单位的所有命中球**做一次射线-球求交（`_unit_hit` 17.3 s，双层 Python 循环），外加一条地形走查（~11 s）；12987 发/120 s | ① 复用本 tick 的命中球表（`world.sphere_table`）而不是逐炮 `unit_spheres`；② 射线-球求交向量化（一次 numpy 解全部候选）；③ 仰角解本身 `(wid, d, h)` 可缓存，但它只占 0.7 %，先别管 |
| 3 | `ai._sees → sight.clear → terrain.los` | 14 %（22 s） | 每次选目标对每个候选做一次视线检查，每次一条 `_march` | 视线结果按 `(观察者格, 目标格)` 缓存 ~0.5–1 s；或把"谁看得见谁"降到每 2–3 tick 一次（不改变武器解算，只改变 AI 感知的刷新率） |
| 4 | `ai._acquire`（`grid.box` + `_unique` + 距离排序） | 10 %（16.6 s） | 每 tick 每个 AI 单位筛一遍 1.5 km 内的所有目标，候选集随单位数涨 | 只对"换了格子/换了目标集"的单位重算；`grid.box` 的结果按 (格子, 半径) 缓存一 tick |
| 5 | `projectiles.run` 主循环 + `sphere_table` | 35 %（54.7 s，其中自身 13 s） | 逐发弹丸一个 Python 循环：制导、地形碰撞、命中解算、写到 ECS 各一段；每 tick 还重建整张球表（`sphere_world` 5.5 s） | 球表按"只有移动过的单位"增量更新；弹丸的直线飞行可以整批向量化（同 tick 内位置是解析的），地形碰撞只对"可能撞地"的那几发做 |
| 6 | ECS 视图税（`__getitem__` / `_gather` / `item()`） | 21 % | 每 tick 1113 万次视图取用、5317 万次 `ndarray.item()` | 系统内用 `groups()` 把 buffer 一次取出（已有范式）；`float(row[0])` 改成取 numpy 标量或用 `.tolist()`；`min/max` 内置调用（2600 万次）换成 `np.clip`/比较 |
| 7 | `raids.run` 规划 | 1.7 % 均值，**单 tick 47 ms** | A* + 两级寻路一次做完 | 每 tick 推进一个 raider 的规划（限制每 tick 的规划预算） |
| 8 | `netcode.snapshot_bytes` | 5.5 %（936 µs/tick） | 每 2 tick 打包 400+ 实体 × 72 B，靠 `.item()` 拼字节 | 不是瓶颈；要削可以整列 `tobytes()` 拼 |

**不建议动的**：`smoke` / `locking` / `blasts` / `debris` / `economy` / `rearm` /
`gunnery` / `mortality` 全部 < 1 %，加起来不到 3 %；`grid.build` 0.5 %。盯着它们优化
是白费力气。

**一句话版本**：先做 (1) 地形射线的向量化 和 (2) 瞄准点求交的向量化 / 复用球表——
两处都是"纯计算、无副作用、不碰随机数顺序"，预计能拿掉 30–40 % 的 tick 时间；`tools/replay.py` 会当场
告诉你有没有改变模拟（它对比的就是数值总和）。
