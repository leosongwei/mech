# 地形系统重构计划

状态：计划，未实现。
范围：**只有地形**。不改任何玩法系统（单位、武器、AI、经济、模式、波次）。

---

## 0. 一句话

把地形从「一张全局数组 + 一个 tile 语义字节」改造成
「**4 km chunk + 高度栅格 + 材质栅格 + 矢量线 + 静态物记录**」：
树 / 建筑 / 巨石从 tile 编码变成**逐对象的记录 + 盒子碰撞箱**（树只记树干），
地面外观不再由贴图决定而是由矢量描述派生。
在现有 16 km 地图上落地，玩家可见行为保持不变。

---

## 1. 目标与非目标

### 目标

1. 地图以 **4 km chunk** 为组织、加载、烘焙、验证的单位。现有 16 km 图 = 4 × 4 = **16 个 chunk**。
2. 树 / 建筑 / 巨石不再编码在 `tiles` 里，而是**静态物记录**，加载时生成**盒子碰撞箱**（树只有树干）。
3. 地面外观由**矢量描述**（覆盖多边形 / 线，带材质 id）派生为材质栅格 + 片元程序化细节，不再依赖贴图或 tile 取色。
4. 服务端物理 API 与弹道行为**逐位不变**，只有一处例外：树干碰撞由圆柱改为方柱（§4.3）。

### 非目标（本计划明确不做）

- 玩法：单位、武器、AI、经济、模式、波次、捕获 —— 一行不改，不引入新的玩法抽象。
- 流式按需加载的**策略**：协议形状按 chunk 定好，本次仍一次性下发全部 16 个 chunk。
- 数百 km 地图、区域进程、并行。
- 破坏系统。只保证静态物 **ID 稳定**，为将来留口。
- 水面、悬崖、飞机、粗 DEM、高度值域放开（§9）。
- 道路系统：`roads` 位掩码与道路渲染本次不动。

---

## 2. 现状与去向

现有地图是四张全局数组（1000 × 1000 tile，16 m/tile，16 km 见方）：

| 现在 | 用途 | 改后 |
| --- | --- | --- |
| `h` 1001² f32 | 高度，**物理权威** | → 每 chunk 的高度栅格（值域、16 m 间距、`HSTEP` 量化都不变） |
| `tiles` 1000² u8 | 8 种语义，**同时**驱动物理阻挡和渲染外观 | → 拆成 **tile flags**（物理）+ **材质栅格**（渲染） |
| `walls` 1000² u8 | 建筑墙高 | → 进建筑记录（`hh`） |
| `roads` 1000² u8 | 道路位掩码 | **不动** |
| （渲染时按 tile 哈希现算） | 树 / 建筑几何 | → **静态物记录**，客户端逐条实例化 |

**核心问题就是 `tiles` 这个字节干了三件不相干的事**：物理阻挡、地面材质、渲染外观。
它们的分辨率需求也完全不同（物理要粗而稳定，材质要高，外观要靠矢量）。
拆开是这次重构的主线。

## 3. Chunk 数据模型

### 3.1 网格

```
TILE   = 16 m
CHUNK  = 250 tile = 4000 m
16 km  = 4 × 4 = 16 chunk
chunk 局部索引  (ci, cj) ∈ [0, 250)
全局索引        i = chunk.i * 250 + ci
```

chunk 网格是规则的，所以 chunk 定位是 O(1) 整除，**不需要哈希、不需要四叉树**。

### 3.2 每个 chunk 的内容

| 层 | 形状 | dtype | 大小（4 km chunk） |
| --- | --- | --- | --- |
| `heights` | 251 × 251（顶点） | u16 量化 | 126 KB raw / ~7 KB zlib |
| `material` | 500 × 500（8 m） | u8 调色板索引 | 244 KB raw / ~5 KB zlib（实测；真实矢量边界更碎，估 5–15 KB） |
| `flags` | 250 × 250 | u8 | 62 KB / ~3 KB |
| `lines` | 变长 | 结构化数组 | 视内容（本次仅少量） |
| `props` | 变长 | 32 B 记录 | 7.5–9.9k 条：235–310 KB raw / **143–182 KB zlib**（实测） |
| `cell_start` | 250²+1 | u16 | 122 KB raw / **~7 KB zlib**（§3.5） |
| `cell_items` | n | u32 | 与 props 同数量级 |

数量来自现有 16 km 图的实测：树 47 752 个树格 ≈ **115 000 棵**，建筑 **4 489**，巨石 **367**，
即每个 4 km chunk 约 7.5–9.9k 棵树 / 280 栋楼 / 23 块石。

**这里有一次可见的代价，必须先说清楚**：现在树是客户端按哈希现算的，占用 **0 字节**；
改成记录后每个 chunk 要背 143–182 KB。整张 16 km 图一次性下发 ≈ **2.9 MB**（zlib 后，
现在是 220 KB），所以 §6 把 chunk 数据改成独立二进制消息而不是 JSON base64。

这两条要一起看：

- 收益是**树变成了数据**：位置、尺寸、ID 都可查、可改、将来可摧毁（现在的哈希做不到）。
- 若嫌大，第一优化是把记录量化成 16 B（tile 内 u16 偏移、cm 为单位、`yaw` 一字节），
  体积约减半。这个优化随时可做，不改变任何接口，**建议等 Step 2 跑通、量过实际带宽再决定**。

### 3.3 `flags`：tile 的物理语义

只留两类位，其余全部迁走：

| 位 | 名称 | 含义 |
| --- | --- | --- |
| 0 | `SOLID` | 地面本身不可通行（原 `TILE_ROCK` / `TILE_SOLID`） |
| 1 | `CANOPY` | 视线在这一格被树冠挡到 `TREE_H`（原 `TILE_TREE` / `TILE_FOREST`） |
| 2–7 | 保留 | 水面 / 摩擦 / 半通行等，将来用 |

**`CANOPY` 是刻意保留的整格位**：现在 `sight_wall` 对树格返回 `TREE_H`（整格），
保留这一位就能让视线逻辑逐位不变，不需要为树冠建几何。

### 3.4 静态物记录（`props`）

32 字节定长记录，服务端与客户端共用字段语义：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | u32 | **稳定 ID**，烘焙后永不重排（将来破坏日志的引用键） |
| `type` | u8 | 0 树 / 1 建筑 / 2 巨石 |
| `flags` | u8 | bit0 实心（挡弹、挡移动） |
| `pad` | u16 | 对齐 |
| `x`, `z` | f32 | 世界坐标（盒子中心） |
| `hw`, `hh`, `hd` | f32 | 盒子半宽 / **从地面起算的高** / 半深 |
| `yaw` | f32 | 绕 Y 旋转（建筑朝向；树为 0） |

- **树**：盒子 = 树干外接方柱，`hw = hd = r`（0.35–0.6 m），`hh` = 现 `_trunks` 的树干高（0.4 × 树高）。
  **树冠不是盒子**——它只挡视线，由 `flags.CANOPY` 表达。
- **建筑**：盒子 = 足迹 + 墙高。本次仍是 1 tile 一座：`hw = hd = 8 m`、`yaw = 0`、`hh = 旧 walls 值`，
  于是盒子正好覆盖整格，等价于现在的行为（§4.2 的等价性要求）。
- **巨石**：盒子。

几何本身**不进数据文件**：客户端照旧用图元拼（`MESH_CYL` / `MESH_FACADE` / `MESH_ROCK`），
数据里只有记录和尺寸。这满足「作为记录，不作为几何」的要求。

### 3.5 按 tile 分桶的索引

物理查询是热路径，不能退化成遍历。静态物本来就按 tile 生成，chunk 内额外存一张
CSR 索引：

```
cell_start : u16[250*250 + 1]     // 每 tile 在 cell_items 中的起点（每 chunk < 65k 条）
cell_items : u16[nprops]          // props 下标
```

`u16` 够用：一个 4 km chunk 的静态物 < 10k 条。
查询代价 = 定位 chunk（O(1)）→ 定位 tile（O(1)）→ 遍历该格的 0–5 条。
**不引入空间哈希、不引入 BVH。**

注意这条索引是**必须的**，不能省成「按 8×8 tile 分桶再线性扫」：森林一格 3–5 棵，
一个桶能有几百条，而 `ground_hit` 每 8 m 就要调一次 `obstacle_at`，会在森林里退化。

## 4. 服务端

### 4.1 结构

```
terrain.py
  Terrain   —— 外部契约。签名与语义不变，内部持有 chunks
  Chunk     —— heights / material / flags / lines / props / cell_*
  generate()—— 生成逻辑基本不变，产出后切块
```

`Terrain` 只留轻量全局信息（`w`、`d`、`bases`、`lanes`、`lanes_rev`、`towns`）与 `chunks[4][4]`。

### 4.2 必须保持的 API（不许动的清单）

以下被 12 个模块使用，**签名、返回值、语义全部不变**：

```
height_at(x, z)          wall_at(x, z)        obstacle_at(x, z)
blocked(x, z)            inside(x, z)
trunk_blocked(x, z, rad) trunk_hit(...)       _trunks(i, j)
sight_wall(x, z)         sight_at(x, z)       los(a, b, step)
ground_hit(p0, p1, ...)  tile_type(x, z)
w, d, h, roads, lanes, towns, bases, TILE
```

`tiles` / `walls` 两个属性**从 `Terrain` 上移除**——外部唯一的使用点是
`netcode.static_payload()`（`backend/server/netcode.py:61`），随协议一起改掉。其余模块只用函数。

实现从「数组查表」换成「定位 chunk + 静态物盒子」，接口一字不改。
`wall_at` / `obstacle_at` / `ground_hit` 是弹道唯一的入口，
**改动集中在这三个函数里，所有弹道、预测、AI 视线就一起跟上了**——这是现有设计的好的部分，要保持。

### 4.3 唯一的行为差异

树干碰撞由**圆柱**改为**方柱**：

| 查询 | 现在 | 改后 |
| --- | --- | --- |
| `trunk_hit` | 平面内线段 vs 圆，再验高度 | 线段 vs AABB（slab），再验高度 |
| `trunk_blocked` | 圆心距 ≤ `rad + r` | 圆 vs AABB（clamp 距离） |
| `wall_at`（树） | 点在圆内 | 点在盒内 |

最大差异出现在树干的四个角：`r(√2 − 1) ≈ 0.41 r ≤ 0.25 m`。
这是产品可见的极小变化，落地时按仓库规则在 `doc/product/CHANGELOG.md` 记一条。
`map.js` 必须实现同一套测试，否则弹着点预测会漂。

**其余全部逐位不变**：高度采样、地面命中、建筑柱体、视线被树冠切断。

### 4.4 等价性要求

为了让 Step 2 的一次提交就能用对拍脚本证明「行为不变」：

- 建筑盒子必须**正好覆盖整格**（`hw = hd = 8 m`，中心在格心），且 `yaw = 0`，
  于是 `blocked` / `wall_at` 的点测试与旧的整格测试完全等价。
- `flags.CANOPY` 必须精确等于旧 `tiles == TREE or tiles == FOREST`。
- 树的盒子中心与 `_trunks` 输出的圆心**完全一致**，只有圆的形状变成方的。

## 5. 客户端

### 5.1 加载

`map.js` 的 `MapData` 改为持有 chunk 数组；`heightAt` / `wallAt` / `obstacleAt` / `blocked` /
`trunkHit` 按新结构重写，**结果与现在一致**（树的两处按 §4.3 同步改成盒子）。

### 5.2 地面渲染

**保留现有两遍结构**——径向 LOD 网格（`TERRAIN_VS`）+ 跟随 tile 补丁（`TILE_VS`）。
它们已经是 heightfield 的正确表示，且顶点吸附解决了远景爬行，不要动。改的是数据来源：

1. 高度纹理：整图一张 → **chunk 图集（atlas）**。4 × 4 个 chunk，每格 251 × 251，
   合计 1004²，和现在的 1001² 几乎一样大。每个 chunk 的边缘顶点与相邻块**重复存一份**，
   于是双线性采样跨块边界不需要任何特殊处理（不重复就会在图集格缝上渗色）。
   shader 里 `texH` 从「世界坐标 → 纹理坐标」改成「世界坐标 → chunk 索引 → 图集格内坐标」。
   将来地图变大，图集换成**环形图集**（固定 4 × 4 或 8 × 8 格，随视点滚动），shader 逻辑不变。
2. 新增**材质纹理** `R8UI`（8 m/texel，每 chunk 500²，同样进图集）+ 调色板 uniform
   + 片元程序化细节 `detail(world_pos, material, slope)`：草纹、砂砾、垄沟、岩石颗粒。
3. **删掉 `TERRAIN_FS` 里按 tile 语义取色的逻辑**（草地/路/建筑/树的色块），
   颜色只由「材质栅格 → 调色板」和「程序化细节」给出。
4. `uTiles` 语义纹理只留给物理和调试，不再驱动渲染。

材质按**最近邻**采样，所以分界是硬的——与现有方块化审美一致，且零成本。
（将来若要柔和过渡，再在烘焙器里加一层边界距离场，渲染侧不变。）

### 5.3 静态物渲染

`renderer._buildProps` 从「按 tile 哈希现算」改为「**读 chunk 的 props 记录逐条实例化**」：

| type | 网格 | 尺寸来源 |
| --- | --- | --- |
| 树 | `MESH_CYL`（树干）+ 现有树冠 | `r` / `hh` |
| 建筑 | `MESH_FACADE` + 屋顶板 | `hw` / `hh` / `hd` / `yaw` |
| 巨石 | `MESH_ROCK` | `hw` / `hh` / `hd` |

保留现有的 per-mesh 批处理与 640 m 分桶剔除（`CHUNK_TILES = 40`），
实例总数不变（11.5 万棵树），性能特征不变。

**注意分桶与 chunk 是两个不同的东西**：chunk（4 km）是数据与加载的单位，
640 m 桶是渲染剔除的单位，不要合并。

## 6. 网络协议

`netcode.static_payload()['map']` 只留元信息（tile 尺寸、chunk 网格、调色板、各层 dtype），
chunk 数据走**独立的二进制消息**，不再塞进 init 的 JSON base64：

```python
# init（JSON）里：
map = dict(tile=16.0, chunk=250, chunks_x=4, chunks_z=4,
           layers=dict(heights="u16:251x251", material="u8:500x500",
                       flags="u8:250x250", props="r32"),
           palette=[...], props_per_chunk=...)

# 随后 16 条二进制消息（每条一个 chunk）：
#   u8 layer_count, 然后每层: u8 layer_id, u32 byte_len, payload
```

理由：base64 会膨胀 33%，且 JSON 里塞 4 MB 字符串对浏览器是个负担。
二进制消息和现有 snapshot 走同一条通道，实现量很小。

本次仍然一次性下发全部 16 个 chunk（16 km 图），**但形状已经是「按 chunk 的」**：
将来换成分批 / 按需 / 预取，只改发送时机，不改协议。

`tiles` / `walls` 两个字段从协议里消失；`roads` 保留。

体积：约 2.9 MB（zlib 后）/ base64 化则接近 3.9 MB —— 这是推动二进制消息的直接原因。

## 7. 实施步骤

每一步都能单独跑起来、单独验证、单独回滚。

### Step 1 · chunk 化（服务端，行为零变化）

生成器输出后切块；`Terrain` 内部改为 chunks；查询改为「定位 chunk → 子数组」。

**新增 `tools/terrain_diff.py`**：对新旧两套实现随机抽 10 万点，对比
`height_at` / `wall_at` / `obstacle_at` / `blocked` / `inside` / `ground_hit` / `los`，
要求**逐位相同**。

### Step 2 · 静态物记录（服务端）

生成器不再写 `TILE_BUILDING` / `TREE` / `FOREST` / `ROCK` 与 `walls`，改为产出
`props` + `cell_start` / `cell_items` + `flags`；`blocked` / `wall_at` / `sight_wall` /
`_trunks` 改读 props。

**验证**：对拍脚本按 §4.4 的三条等价性要求全绿；树的差异只出现在预期的角区（≤ 0.25 m）。
跑一局，AI 与坦克全程正常，日志无异常。

### Step 3 · 材质栅格（服务端 + 烘焙）

生成器额外产出**矢量覆盖层**（多边形 / 线 + 材质 id），烘焙器把它光栅化成 8 m 材质栅格。
矢量是权威，栅格是派生产物——**这条关系是将来接入手工地图的前提**。

起步不必一步做到完整多边形：生成器现在就是用圆斑、线段、走廊这些图元在栅格上打掩码的，
把它们改成「输出图元列表，再由烘焙器光栅化」即可。图元集合很小（圆、胶囊、多边形），
真正接入 OSM 级别矢量时只需要换掉「谁产出图元」，栅格化与运行时都不用改。

**验证**：材质栅格与旧 `tiles` 的语义一致性 ≥ 95%；`flags.SOLID` 与旧 `BLOCKING`
在每一格上等价。

### Step 4 · 客户端加载器

`map.js` 改 chunk 结构；`_buildProps` 改读记录。

**验证**：同机位截图与改造前**接近逐像素**（树与建筑的位置必须完全一致，
因为 props 仍由同一套哈希生成）。

### Step 5 · 矢量地面渲染

材质纹理 + 调色板 + 程序化细节；删除 tile 取色逻辑。

**验证**：地面 / 低空 / 20x 光学三组截图；检查田界、林地边界、城区边界无接缝、
无闪烁、无平铺感；远处（3 km 外）细节不糊。

### Step 6 · 收尾

删掉 `walls`、旧 `tiles` 语义的残渣；更新 `AGENTS.md` 里地形那一节；
在 `doc/product/CHANGELOG.md` 记录两处产品可见变化（树碰撞改方柱、地面配色改由材质驱动）。

## 10. 需要先确认的一个决策

**`props` 表放在地形层（chunk 内的只读记录 + CSR 索引），不进玩法 ECS。**

理由两条：

1. 本计划不引入新的玩法抽象，静态物现在既不能被瞄准也不能被摧毁。
2. 量级不匹配：树有 11.5 万，ECS 容量是 8192，且 64 个组件位已用掉 51 个。
