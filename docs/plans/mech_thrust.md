# 机甲运动：马力曲线、重力、阻力

1.27.0 起机甲不是"朝指令速度逼近"，而是一台**发动机**：腿给一张功率曲线，推力是
功率除以速度，方向就是**指令方向**（飞行员的车身坐标系），速度方向的改变只由这份推力
产生。这一页记下模型的来历、常数怎么解出来、以及为什么代码是五个 system 而不是一个。

## 1. 三个力

机甲是地面单位，`pos` 永远贴在高度场上，所以运动只有一个自由度：**水平面上的速度**
（`vel` 的 x/z）。垂直分量是它走过的坡（`Integrate.step` 按地形重新写）。

| 力 | 方向 | 大小 | 出处 |
| --- | --- | --- | --- |
| 推力 | 指令方向（**机身坐标系**里由 `W A S D` 给出），**沿坡面** | `F(v) = min(P(v)/v, 1.5 g·m)` | `Mech.Thrust` |
| 重力 | 铅垂向下，取沿行进方向的分量 | `g·sinθ = g·s/√(1+s²)` | `Mech.Slope` |
| 阻力 | 与速度相反 | `MECH_DRAG = 3.182e-3 /m`，即 `a = k·v²` | `Mech.Drag` |

水平面上的运动方程：

```
dv/dt = F(v)/m · f · u · cosθ - g·sinθ - k·v²
```

* 推力是一张**功率曲线**（1.27.0 后期改成这个，之前是恒推力）：

  ```
  P(v) = 5000 + 3000 · v / 50  hp        v ≤ 50 m/s
       = 8000 hp                          v > 50 m/s（封顶）
  F(v) = min(P(v)/v, 1.5 g · 15000 kg)   （动力上限，重力不计入）
  a(v) = F(v) / 15000 kg
  ```

  恒推力的毛病是**手感没有两端**：起步和极速前都是同一个 0.8 g，既不像发动机也不像
  机器。功率曲线让低端变猛、高端变绵，而且它自己**没有极限速度**——极限速度是阻力给的。

  纯功率曲线在 v→0 处发散（静止时推力无穷大，实测 5 g 起步"太挂了"），所以动力本身
  再压一个 **1.5 g**（`MECH_G_LIMIT`，**重力不计入这个预算**：坡上的重力照常加/减）。
  于是两条限制各管一段：**76 km/h 以下是 1.5 g 的恒加速度**，上面是发动机——
  108 km/h 1.15 g、144 km/h 0.94 g、180 km/h 0.81 g。

* `f` 是**腿的对齐系数**（`0.45–1.0`）：腿是推力机构，指令方向一变腿先转过去
  （`Integrate.turn_legs`，2.6 rad/s），没转到位之前只有部分推力；
* `u` 是**油门**：满推杆时恒为 1，巡航速度由调速器给，并且**每 tick 只取还差的量**，
  不会冲过头（1.5 g 下一 tick 的推力是半个调速带，冲过去就会来回振）；
* `cosθ = 1/√(1+s²)`：推力按**斜面**算，只有 `cosθ` 那一份落在水平方向上；
* `s` 是地形沿行进方向的坡度（`Terrain.slope_along`），`sinθ = s·cosθ`。

## 2. 常数是怎么来的

设计要求只剩一条**极速**：平地 **180 km/h**。功率曲线的两端由设计给（`MECH_HP_LOW`
5000 hp、`MECH_HP_HIGH` 8000 hp），质量 15 t，于是阻力系数被**解**出来：

```
平地平衡   P(v0)/v0 = m · k · v0²,   v0 = 50 m/s
        =>  k = 8000 hp / (50 · 15000 · 50²) = 3.1817e-3 /m
```

`Defs.MECH_DRAG` 就是这一行算式写在代码里（编译期常量表达式），所以"平地 180"
永远不会和常数表漂开。**坡上的数字全是推论**，不是约束：

| 沿行进方向的坡度 | 平衡速度 |
| --- | --- |
| 35° 上坡（0.70，机甲爬坡上限） | **114 km/h** |
| 30° 上坡（0.58） | 125 km/h |
| 20° 上坡（0.36） | 146 km/h |
| 平地 | **180 km/h** |
| 24° 下坡（0.45，实测行） | 205 km/h |
| 30° 下坡 | **210 km/h** |
| 40° 下坡（地形上限） | 215 km/h |

**上坡停不住**：1.5 g 是**动力**上限，重力另算，所以 35° 坡上起车的净加速度是
`1.5g·cos35 − g·sin35 = 6.4 m/s²`——而 35° 正是它允许的最陡坡，"被重力拖停在坡上"
这件事在机甲能上的坡里不存在。

## 3. 油门与刹车

`vel_cmd` 的模长是"要把车开到多快"：

* `|cmd| ≥ 极速 - 0.5` → **满推杆**，`u = 1`，调速器让位：推力恒在，坡和阻力决定结果。
  这就是"下坡能跑过 180"的原因（210 km/h 时动力只剩 0.66 g，远在 1.5 g 之下，
  所以那个限制在高段根本不参与）；
* `|cmd| < 极速 - 0.5` → **巡航调速器**：`u = clamp((cmd - v_∥)/3, -1, 1)`，且
  `Δv` 不超过还差的那一点。平地指令 12 m/s 稳定在 11.9 m/s；
* `|cmd| < 0.05` → **撑地刹车**：`MECH_BRAKE = 12 m/s²`（1.22 g），和 1.5 g 的起步
  几乎对称：180 km/h 到停下 78 m / 3.5 s。

## 4. 转向就是推力方向

只有一台作动器：腿推**指令方向**。想换方向，就是让指令方向换掉——也就是让**机身**转过去
（`Gunnery` 以 80°/s 追观瞄），推力随机身转，速度再被推力掰过去。飞行员的手感因此是
"鼠标转的是车身，车身转的是推力，速度是最后跟上的那一个"：`W A S D` 读的是机身坐标系
（`frontend/src/input/sight.js::moveVector` 拿线上最新的机身 `yaw`），所以 `A` 在车头
朝东时把机体推向正北，`ALT` 自由观察不影响行进方向（推杆本来就不读视线）。

速度方向的改变只能来自推力，于是在指令方向的坐标系里（`u` 沿新方向、`w` 垂直于它）：

```
du/dt = F(v)/m - k·v·u
dw/dt = -k·v·w          （只有阻力吃掉那一份横向速度）
```

两条一起给出"转一个直角要多久"。从平衡速度起把指令转 90°：

| 进入速度 | 速度方向转 45° | 完全摆正（残余 5° 侧滑） | 出弯速度 |
| --- | --- | --- | --- |
| 176 km/h | **4.10 s**（理论 4.07） | 16.7 s | 178 km/h |
| 73 km/h | **1.40 s**（理论 1.38） | 11.9 s | 177 km/h |

横向那一份只能靠阻力衰减（时间常数 `1/(k·v)`，180 km/h 上约 6.4 s），所以高速转弯是
**宽而慢的斜切**：车身先摆过去、机身横向滑一段，速度几乎不掉。这是"只有推力"的必然
结果，也是它能给出的全部——要转得更紧，只能给腿一份**侧向**预算（`MECH_TURN_G` 那一版
3 g 就是那么做的，手感"异常强力"，已去掉）。横向加速度在低速端照样是 1.5 g：静止时按
`A` 就是 1.5 g 的正经侧推，速度越低越灵敏。

## 5. 为什么是五个 system

一条定律一个 `run`，按 tick 顺序注册在 `World._build_pipeline`：

```
Steer  →  Thrust  →  Slope  →  Drag  →  Ground
```

* `Steer`：AI 的意图（`Drive.legs`）转成 `vel_cmd`，腿按机器自己的速率转向；
* `Thrust`：腿的推力 / 调速器 / 撑地刹车，沿**指令方向**改速度，写进 `vel`——速度的方向
  也由此被掰过去；
* `Slope`：重力沿地面那一份，写进 `vel`；
* `Drag`：平方阻力，从 `vel` 里扣；
* `Ground`：`Integrate.step` —— 唯一一个真的移动 `pos` 的。

它们之间**不共享任何中间变量**：速度缓冲就是力的累加器，因为每一条力都只是"往速度上
加一个与 dt 成正比的量"，而 dt 全 tick 一致、顺序无关（除了 `Ground` 必须最后）。
一个额外的累加组件（`thrust[3]`）会是同样三个 float 的第二份拷贝。

这样做的好处是每一行都能单独读、单独改：

* "上坡为什么慢"在 `Slope`；"平地为什么是 180"在 `Drag` 与 `Defs.MECH_DRAG`；
  "为什么下坡能跑过 180"在 `Thrust` 的满推杆分支；"转一个直角要多久"也在 `Thrust`；
* `--check drive` 一行为一条定律：平地 / 上坡 / 下坡 / 刹车 / 巡航，实测与代数并列；
* 车（`Vehicle.cs`）仍然是自己的自行车模型，步兵（`Foot.cs`）不变：这一串只跑在
  `MoveColumns.OnMech` 上，即"有机甲手臂血池"那一个原型。

`theory` 那一列是把同一张力曲线解零点得到的（`Mech.Thrust.Force` 只有一份实现），
所以它证明的是**积分器和调速器**忠实于这条力，而不是另一套代数。`flat` 的 49.67 与
50.00 之差是两个离散化：`vel` 每 tick 先加 `F/m·dt` 再扣 `k·v²·dt`，稳态读出来比连续
解低一个 `F/m·dt`（0.27 m/s），剩下的是腿的对齐系数（`turn_legs` 收敛到 2.6·dt 以内）。
0.7% 的错，落在 2% 的判定带里。

`redirect` 两行是第 4 节那条积分在同一个速度缓冲上重算一遍的结果（在指令方向的坐标系里
从平衡速度起把指令转 90°，`u` 长 `w` 消），实测与代数差 1 % 以内。这一行量的是**推力**本身，
所以 `--check drive` 先把 `leg_yaw` 摆到新方位再计时：摆腿那零点六秒属于 `Legs` 的对齐
系数，飞行员在游戏里会连带感受到，但不该混进这条定律的判定。
