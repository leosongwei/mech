# 地形重构与单位寻路:连续高度、坡度、三角网导航

日期:2026-07-29
状态:计划(未实施)
范围:**现有 16 km 地图的玩法不变,地图尺寸不动。**

一句话目标:
1. 地面从"4 m 台地"变成**连续高度**,坡度自由(更缓也能更陡);
2. 新增**底盘坡度上限**:陡坡不可行走,反过来低坡到处可走;
3. 用**三角网 navmesh + 三角邻接 A\*** 取代现在"反应式扇形避障 + 只有 raider 才有的格子 A\*";
4. 顺手修掉地形 LOD 接缝的豁口(单层吸附 + skirt)。

300 km 尺度**明确推迟**(§9),但有三处"现在不做、将来会堵死"的假设要在本计划里顺手清掉。

### 0.1 地形的形状(2026-11-12,第五步)

坡度、寻路、LOD 四步做完之后,地图的**观感**还不对:整张图是同一尺度的小包,
没有"大片平原 + 成片丘陵"的层次。根因是噪声的**振幅衰减**——自己写的 `_fbm` 每个
倍频振幅减半,而波长也减半,于是每一层对坡度的贡献完全相同,叠出来就是一张皱毯子。

改成 OpenTTD 的 TerraGenesis 结构(`src/tgp.cpp`):

* **振幅表**用它的 "very rough" 一行(`1, 0.50, 0.40, 0.333, 0.167, 0.0107, 0.0067`),
  即波长每减半、贡献降到 1/2 → 1/8,公里尺度是主体,米尺度只是纹理;
* **每个倍频的栅格各自旋转**(`_octave`),否则所有层的格线对齐,地图读起来是方格被面;
* **分层曲线**(`_curve_map`):四张 TerraGenesis 的 curve map,从"平原"(把拿到的
  高度压到 1/5)到"山脉"(一半地面落在最高 1/5 的高度),用一个千米尺度的掩码混合;
* 掩码取**地形自己的前三个倍频**,所以山不会长在本来就平的地方。

结果(`--check terrain`,MECH_TERRAIN_MAP 可把四个种子的地形画成地形图):
平均坡度 0.091、最高 196 m、平原(0.00–0.05)仍占 40%、APC 爬不上的地方 0.1%,
三条车道最陡 0.38/0.26/0.50;`--check nav` 的可达面积 99.2%,跨图 1.02×。

**已知的后续**(不在本次范围):步兵在市镇/森林边缘仍会以 15 s 的节奏反复请求绕行
(实测一次战斗 4 分钟 1251 次,其中步兵 1382/… 见 `--check nav` 的 by type 一行);
这些请求被 tick 预算封顶,不构成卡顿,但"为什么会一直卡"值得单独查一次
(候选:16 m 瓦片级的 `blocked` 把整片树林当墙,而树干之间其实是空的)。

## 1. 现状:台阶只有三处

高度场**已经**是连续可采样的:`Terrain.height_at`(`Core/Terrain.cs:429`)在四个顶点高度上双线性,
客户端 `map.js:191` 逐行镜像。所以"变成平滑地面"不是换数学,而是去掉三处量化:

| # | 位置 | 现在 | 换成 |
| --- | --- | --- | --- |
| 1 | `Terrain._terrace`(`Terrain.cs:1291`,在 `:2319` / `:2563` 调用) | 每个顶点 `round(h/HSTEP)*HSTEP`,`HSTEP = 4` | 删掉 |
| 2 | `Netcode.static_payload`(`Net/Netcode.cs:97-101`) | `int16` **整米** | u16,`H_UNIT = 0.05 m` |
| 3 | `Drive.clear`(`Systems/Movement/Support/Drive.cs:36`) | `abs(height_at - y) < 4f`,绝对台阶 | 梯度上限(坡度) |

`HSTEP` 全仓只有 5 处引用,全部在 `Core/Terrain.cs`。"平滑"这一半的改动量很小。

### 1.1 现有 LOD 的豁口有确切机制(一起修)

1. **每带各自吸附** — `TERRAIN_VS`(`renderer.js:90`)`base = floor(uCam.xz / spacing) * spacing`,
   而 `spacing` 由 `abs(aCell)` 逐顶点算出,所以相邻带(16/32/64/128 m)的顶点被吸附到**不同的栅格**上,
   带边界上的四边形可以拉长到一整格(外圈几百米),并且随相机移动每秒重排一次,所以它在抖。
2. **near patch 与 far core 差一格** — `_drawTerrain`(`renderer.js:1142`)用 `Math.round(eye/tile) - K` 定位 1.5 km 补丁,
   far 核心按 `floor(eye/tile)*tile` 对齐。
3. 两遍都没有 skirt,切边直接可见。

## 3. 数据模型

### 3.1 高度

* 单张连续高度栅格,仍是 `TILE = 16 m` 顶点网,`MAPW/MAPH` 仍是 1000。
* 线格式:分块不需要,`u16 × H_UNIT` 直接整张图(`1001² × 2 B = 2 MB` raw),`H_UNIT = 0.05 m`,
  范围 0–3276 m。客户端 `map.js load` 读同一个单位。
* `CONTACT_QUANT` 4 → 8 m(`Netcode.cs:72`;u16 上限 262.1 km → 524 km)。现在的 4 m 是一颗将来的哑弹,
  改成 8 m 是一行,且对 HUD 无可见影响 → 现在就改。

### 3.2 物理规则:三角面,不是双线性

现在 `height_at` 是双线性,而渲染的近景网格是**每格两个三角面**(`_buildPatch` 的 `a,c,b` / `b,c,d`,
NE→SW 对角;`renderer._buildRoads` 的 `facet()` 手抄了同一条规则)。两者今天最多差一个台地台阶;
有了任意坡度,误差会长到米级,而两端必须镜像。

**物理采样改成和网格同一条规则**:落在哪个三角面就用那个平面 —— DCS/Arma 的做法(碰撞面就是可见面)。

```text
         (i,j+1) ---- (i+1,j+1)        对角线: (i,j+1) — (i+1,j)
            |     \      |             tx + tz <= 1  -> 下三角 (a,b,c)
            |       \    |             否则           -> 上三角 (d,c,b)
         (i,j) -------- (i+1,j)        与 renderer.js:635 的 facet() 逐字一致
```

* 服务端 `height_at` / `_march` 的 `sample` / `structure_hit` / `ground_hits_many` 全走这一条;
  成本与双线性相同(四次读、算三次),`_march` 里"缓存上一格四个角"的优化原样保留。
* 客户端 `map.js heightAt` 同改,`tests/cases/height.json` 双端对拍(§10)。
* **物理格仍是 16 m**:`LOS_STEP = 8`(`Sight.cs:26`)、`FirstHit` 的 `step = 9f`(`FirstHit.cs:41`)、
  "一条 36 m 的腿不可能不落进一个 16 m 格"那一类论证全部继续成立。
* 三角面仍是平面,所以"两个采样点都在面上方 ⇒ 中间段在面上方"(凸性)的论证不变,弹道精度不退化。

## 4. 生成器

### 4.1 坡度控制

`_fbm` 的梯度在 16 m 上可以给出 60°+ 的面。两步:

* **地形侧** `MAX_TERRAIN_GRADIENT`(建议 0.60 ≈ 31°;山地 0.85 ≈ 40°):
  一次"局部极限"迭代(每点夹到邻域能支撑的高度)削平超限处,代价 O(n),等价于一次极浅的侵蚀。
* **底盘侧**:`MECH_MAX_GRADIENT` 0.70、`APC_MAX_GRADIENT` 0.58、`FOOT_MAX_GRADIENT` 0.84,
  全部进 `Core/Defs.cs` —— **它是移动层和寻路层共用的唯一来源**(§6.4)。
* 数量级参考:现在台地给的是 14°,所以 0.58 / 0.70 / 0.84 分别意味着"车能爬 30°、机体 35°、步兵 40°",
  空出来的 25–40° 就是"看得见、过不去"的山脊 —— 这正是想要的战术地形。

### 4.2 道路:走廊纵断面

现在是"路面所有角点取同一个台地高度 + 邻格平均 + `_blur3` + 取整"(`Terrain.cs:2318-2370`)。替换为:

* 沿每条 lane 的折线算一个**纵断面**:地形剖面 200 m 滑动平均,坡度上限 6%;
* 走廊内(24 m)向该纵断面融合,路面本身 10 m 内几乎完全贴合;
* `ROAD_WEIGHT` 的语义不变(路面在平均里权重更大),只是不再"压成一格一格"。

### 4.3 城镇:跟着山走

* 只把 `TOWN_PLAZA` 半径(80 m,前哨落点)压平,镇子其余地面朝它收一半 —— 山坡上的镇子照样起伏。
* 建筑落位改成"四个角取最低点",盒子向下延伸落差(`renderer._buildProps` 同改)—— 不悬空、不埋墙。
* `plant`(`Terrain.cs:383`,debug_trees)改块内重建 cull,并把 navmesh 窗口标脏(§6.3)。

其余生成规则(**车道、城镇生长、镜像不变式、`no_build`、树/建筑 hash**)一行不动。

## 6. 单位寻路

### 6.1 今天是什么

| 层 | 谁 | 机制 |
| --- | --- | --- |
| 战略 | `Raid.FieldNav`(`Raid.cs:617-658`) | 128 m 节点,`125² = 15 625` 个;`cost = 1 + 8·wood + 8·build + 0.35·min(12, force)`,`open = solid < 0.5`;**每次计划重建**,~15 ms/次 A\*,两次并行 45 ms |

"基地旁边 4–7 台机体原地磨" 是同一类 bug,当时只修了扇形承诺,没修"规划层缺位")。

### 6.2 判据分裂(必须先修,否则新寻路会把 bug 放大)

规划层和驾驶层对"能不能走"用了**不同的事实**:

| 判据 | 树/森林 | 基地 | 坡度 | 树干 |
| --- | --- | --- | --- | --- |
| `Terrain.blocked`(驾驶用,`Drive`/`Integrate`) | **不可通行** | 可通行 | 不看 | `trunk_blocked` 单独看 |
| `StreetNav`(`Raid.cs:701-708`) | 可通行,cost 3 | **不可通行** | 不看 | 不看 |
| `FieldNav`(`Raid.cs:652-656`) | 加权 8 | 可通行 | 不看 | 不看 |

所以规划器会画出"穿过林子"的路线,而车永远开不进去;也会把基地当成墙绕开。
这是"机体顶在墙上磨"这类现象的结构性来源。

### 6.3 三角网 navmesh

**核心决定:navmesh 存"几何事实",profile 存"能不能过"。** 一份地形网格服务三种底盘。

```text
NavRegion                       // 一个窗口,按需建,cache 里 LRU
  x0, z0, nx, nz                // 16 m 格窗口
  gradient : u8  / 三角         // |∇h| 量化 0..2.0,两位小数够用
  walk     : 2 bit / 格         // 0/1/2/3:两个三角各一位;建筑、石、实心、森林为 0
  clear    : u8  / 格           // 到最近不可走格的距离变换(格数,封顶 255)
  note     : 三角 id = cell * 2 + half
```

* **三角 id 与邻接**:一块三角有三个邻居 —— 对角线对面的那一个(同格),以及两条格边各自对面的三角
  (跨格)。邻接是隐式的,不需要存边表。
* **可行走判据分两步**(§6.4):表面坡度 ≤ profile;`blocked` 类型语义与驾驶层同一个函数。
* **通行宽度**:`clear` 距离变换给出"离最近的不可走格有几格"。规划时要求
  `clear >= max(1, ceil(radius / TILE))`。**在 16 m 的物理格上这一条几乎不咬人**
  (一格就是 16 m,任何机体都塞得下),它的价值有两个:一是给代价贡献一个"偏向开阔地"的项,
  二是为将来物理格变细留位。另外记一个已知错位:物理上一整格建筑格全不可走,
  而画出来的楼是 `tile * (0.88 + r1*0.10)`(`renderer.js:790`),所以**看起来 1–3 m 的房缝其实是 16 m**,
  机体开得进去、但会擦到画出来的墙面。这不是寻路能修的,属于"可见体 vs 碰撞体"的一致性问题,
  留在 Step 2 的建筑落位一起处理。
* **窗口**:`bbox(start, goal)` 加 `NAV_WINDOW_PAD = 320 m`,和今天 `StreetNav` 的 pad 同一手法;
  1 km × 1 km = 4 k 格 = 8 k 三角,`gradient 8 kB + walk 1 kB + clear 8 kB ≈ 17 kB`/窗口,
  LRU 32 个 = 大半个 MB。**窗口化本身就使它不依赖地图尺寸**(§9 的第一条)。
* **构建成本目标**:4 k 格 × (取 4 个高度 + 一次坡度)≈ 0.2 ms,距离变换两遍 ≈ 0.1 ms。
  由 `--check nav` 实测;建完缓存,地形 immutable,只有 `plant` 会标脏。

**为什么不继续用格子**:格子把"坡度"表达成每格一个数,而坡度是方向性的 —— 沿等高线能走、垂直等高线不能。
三角面带法线 + 每条边有梯度,这一个差别就是这个游戏要的东西(山脊能守、缓坡能迂回)。
另外三角面**就是物理面**(§3.2),"规划器认为能走的地方"和"车能开上去的地方"从构造上一致。

### 6.4 一条可行走判据

新增一个函数,三层都只能走它:

```csharp
// Core/NavWalk.cs —— 唯一判据
static bool Walkable(Terrain t, NavProfile p, float ax, float az, float bx, float bz);
//   = 沿途每个三角面坡度 <= p.max_slope
//   && 沿途 !t.blocked(x, z)             (与 Terrain.blocked 同一个 LUT)
//   && 沿途 !t.trunk_blocked(x, z, p.radius)   (树干仍按圆柱解,不做几何)
//   && 每个采样的 clear >= p.clear_min
```

调用者:
* **驾驶层**:`Drive.clear_run` 与 `Integrate.step` 用它(取代散落的 `blocked` 5 点采样 + 树干 + `< 4f`);
* **规划层**:A\* 的边测试与 string-pull 的可视性测试用它;
* **验证**:`--check nav` 的"车道可通行"直接扫它。

判据只有一个,所以不会再出现"规划器说能走、车开不进去"。

### 6.5 A\* 与预算

```csharp
NavRequest { world, eid, from, to, profile,                    // 排队
             gs[], came[], open: PriorityQueue,                // 池化复用
             expansions, state }
Nav.poll(world, NAV_NODES_PER_TICK);                          // 每 tick 推进
```

* **预算式推进**:一次请求每 tick 最多展开 `NAV_NODES_PER_TICK = 2000` 个三角,
  完成后再 `Nav.add(...)` 写进现有的 `nav_route`。一条 1 km 的路径约 3–4 k 展开 = 2 个 tick(66 ms),
  肉眼不可见;60 台机体摊开也吃不满预算。**取代今天 15–45 ms 的同步尖峰**(`Raid.cs:166-168`、`:258-259`)。
* **代价**:`step · (1 + SLOPE_COST · g²) + PROP_COST·该格 note + GRADIENT_COST·min(cap, force)`,
  最后一项复用 `Raid._gradient` 的力场(`Raid.cs:734-778`),于是战术路径也天然倾向掩体方向。
  `SLOPE_COST` 建议 2.0:陡但不超限的坡"能走、不划算",这正是要的迂回行为。
* **平滑**:A\* 之后在三角面上做 string-pull,可视性测试用 §6.4 的 `Walkable`,**不是**今天 `_open_line`
  的"无墙无树"(`Raid.cs:1037-1071`),因为后者不认识坡度。输出点表压到 ≤ 24 点。
* **轮式**:折线加一条后处理 —— 相邻路点长度 ≥ `2 × APC_TURN_R`(22 m),否则合并。
  A\* 的原生波长是 16 m,11 m 转弯半径的车按那个开就是拉力赛;`Nav.route_speed`(`Nav.cs:117-166`)
  的切弯预算接着管速度,不改。
* **池化**:`gs/came/open` 按最大窗口尺寸分配一次,请求之间复用。今天 `_astar` 每次三个数组 +
  `PriorityQueue`,`_gradient` 每次 8 个 15 625 长数组 —— 都是白扔。

### 6.6 三个 profile

| profile | 谁 | `max_slope` | `radius` | 备注 |
| --- | --- | --- | --- | --- |
| `MECH` | 机体(含 AI crew) | 0.70 | `0.6·UNIT_DEFS.radius`(与驾驶层同一个数) | 14 m 转弯半径,折线要后处理 |
| `APC` | 轮式 | 0.58 | 同上 | 后轴自行车模型,侧倾上限可选 |
| `FOOT` | 步兵 / 平民 | 0.84 | 很小 | 能上山脊,机甲不能 —— 这是要的战术不对称 |

`radius` 用 `Integrate` 里那 5 点采样环的同一个系数(`0.6 * radius`),**再一次"一个数两处用"**。

### 6.7 什么时候重规划

| 触发 | 今天 | 改后 |
| --- | --- | --- |
| 出生 / 车道行进 | lane 折线 | 不变(车道是**走廊**,不是路径) |
| 顶住不动 `STUCK_SKIP = 2 s` | raider 丢一个路点;其他**什么都不做** | 共享 `Stuck`,所有 crew 发起一次 ≤ 300 m 的绕行请求 |
| `STUCK_REPLAN = 6 s` | raider 用 `StreetNav` 本地重规划 | 三角网局部重规划(窗口以自身为中心) |
| raider 战略重规划(12 s / HOLD 到期/目标易主) | `Raid._replan` | 不变;末端 400 m 的 `StreetNav` 换成三角网 |
| 目标移动 / 新威胁 | — | 不触发作路径重规划(路径只到目标点,追击由 `Front`/`Engage` 换点) |

原则:**战略层改变目标,战术层改变路线,反应层改变方向**。三层各自的输入不同,所以不会互相打架。

### 6.8 与战略层的关系

* `FieldNav` 128 m **保留**:它回答"哪边是敌、该往哪座镇"(`GRADIENT_COST` 那套已经调过:
  13.8 km 直行 / 0.35 权重 15.5 km / 0.5 以上 25.8 km)。
* `StreetNav` **退役**,被 `NavRegion` 取代(同样窗口化,但 16× 分辨率、认识坡度和清距)。
* 顺带修掉 `Raid` 两个已知浪费:第二个 hull 落地会重建一遍 `_nav`(`:456-459`,`_replan` 没接住
  已经算好的网格);`Raid.ARRIVE`(`:115`)声明后从未使用。

### 6.9 白送的东西:反斜面与掩体

`gradient` 字段 + 现成的 `Sight.clear` 就能回答"这个三角能不能把车藏在一道山脊后面" ——
即用户说的"反斜面"。三角网建好之后,这是**纯查询**,不新增结构。本轮**不做**(选点时机的
`Front`/`Engage` 改造是另一件事),但在 §9 记为下一步的自然延伸。

## 7. 客户端渲染

### 7.1 LOD 接缝(修,不推翻)

结构保留径向网格 + 近景补丁,只改三处:

### 7.3 客户端镜像

* `_buildRoads facet()`(`renderer.js:635`)升级为**唯一权威**的三角面规则,服务端与 `map.js` 都照它。

## 9. 推迟:300 km(只保留三条"不堵死"的决定)

地图尺寸本轮不动。将来要做的话,结构上必须留的门只有三条,都很便宜:

1. **新代码不要有整图数组**。`NavRegion` 是窗口化的,A\* 是窗口化的,天然无尺寸依赖;
   反例是 `Grid`(128 m 格)、`Raid.FieldNav` 的全图节点、`static_payload` 的全图四张平面 ——
   这些留到真做的时候再换(方案已经想好:稀疏格 / 局部窗口 / 分块流式,见 git 历史里的
   `doc/terrain_plan.md` 和本文件早期版本)。
2. **`CONTACT_QUANT` 现在就改 8 m**,避免将来一道静默溢出。
3. **采样步长不要写死成"半个瓦片"以外的东西**。`LOS_STEP`、`FirstHit` 的 `step = 9` 都从 `TILE` 派生即可。

真做 300 km 的时候,`TILE = 16 m` 的物理格和 `height_at` 的签名都不必改 —— 那是这个设计留的最大余地。

## 11. 风险

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| 判据再次分裂 | 规划器与驾驶层对"能走"看法不同 → 机体顶墙磨 | 一条 `NavWalk.Walkable`,三层唯一入口(§6.4);`--check nav` 的 `lane` 列就是它的回归 |

| 窗口边界效应 | 目标在窗口外 | 战略节点做窗口的远端点(§6.8),窗口以"起点→战略节点"为轴 |
| 轮式曲率 | A\* 折线波长 16 m,转弯半径 11 m | 折线合并到 ≥ 22 m;`Nav.route_speed` 接管速度 |
| A\* 分配 | 每次 3 个数组 + 队列 | 池化,按最大窗口一次分配 |

| 建筑悬空/埋墙 | 坡上的房子 | 四角最低点起墙(`renderer.js`) |
| `vel[1]` 变连续 | 下游把爬升率当速度 | `--check fcs` / `intercept` 复测,产品记一条 |
